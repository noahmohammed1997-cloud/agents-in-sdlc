最初にプロジェクトに小さな機能を追加しました。より大きな変更には、より確実なプロセスが必要です。GitHub Copilot app は組織の既存の作業手順に沿って動作し、必要なものを適切な方法で構築できるように設計されています。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスに沿って作業します。Issue を起点に新機能を実装し、コードの妥当性と機能の動作を確認してから、プロジェクトにマージします。

> [!NOTE]
> 機能開発を続ける間は、同じセッションを使います。通常はファイルの種類ごとに異なるセッションやプルリクエストを作成しますが、ここでは中核となる概念に集中するため手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub Issue から新しいエージェント セッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで機能を実装します。
- コードをレビューします。
- ブラウザー Canvas で機能を手動検証します。

この機能の作業を続けながら、リポジトリの命令を更新し、既存の `quality-checks` スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、利用者はカテゴリや発行元でゲームを絞り込む必要があります。バックログの Issue には機能が説明されていますが、カテゴリを組み合わせる方法など、コーディング前に合意が必要な詳細もあります。Plan モードで仕様を決め、その後、範囲を定めた実装を Autopilot に許可します。

## 背景

AI コーディング エージェントを開発の流れに導入しても、開発の基本は変わりません。むしろ、これまで以上に重要になります。多くの開発者は、次のような流れで作業します。

1. 実装内容の詳細を記述した Issue を開きます。
2. 構築する内容を計画します。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新しい機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードがレビューされ、継続的インテグレーション プロセスが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合はここに示した流れを基本にしています。

この標準的な進め方に沿うことで、AI が生成したコードが要件を満たし、手作業で書いたコードと同じレビューと検証を受けるようにできます。

## セッション モード

**セッション モード**は、エージェントにどの程度の自律性を与えるかを制御します。プロンプト フィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: 開発者とエージェントが協力して作業します。エージェントは変更を提案し、次の作業に進む前に入力を待ちます。
- **Plan**: エージェントが先に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律的に作業し、入力を待たずにコードを書き、テストを実行して反復します。

最初に Plan モードで計画を確認し、その後 Autopilot で実装します。

## Issue からセッションを開始する

作業を始める前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** の下から Tailspin Toys リポジトリのフォルダーを選び、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに含まれる Issue なので、新しく作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

   ![GitHub Copilot app の Issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モード選択から **Plan** を選びます。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションで動作しない場合は、アプリの PATH またはバージョン管理ツールの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルタリング機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチをレビューできます。Issue から開始したため、Copilot は機能のリクエストをすでにコンテキストとして持っています。次のプロンプトを送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画を Issue の受け入れ条件と照らし合わせます。カテゴリと発行元によるフィルタリング、アクセシブルなコントロール、データ アクセスの変更、テストが含まれていることを確認します。カテゴリの組み合わせ方法や、該当するゲームがない場合の動作など、不明確な点を話し合います。

計画には、プロジェクトの既存ツールを使った lint、単体テスト、E2E テスト、型チェックを含めます。フィルタリングの実装とテストに範囲を絞り、品質確認の手順を完了してから PR を作成します。計画の修正は承認前に依頼し、後で検証できるよう Issue の URL と合意した説明を手元に控えます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンで表示される同等の項目を選択します。承認しただけでモードが切り替わると思い込まず、モード表示が **Autopilot** になっていることを確認します。

Copilot は実装を開始し、合意した計画に沿ってコードを生成してテストを実行します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードは、ほかのコードと同じようにマージ前にレビューします。コードを確認し、サイトを起動して動作も確かめます。

1. **Changes** を開き、フィルタリングの実装とテストを確認します。
2. 複数カテゴリや発行元の組み合わせを含め、結果を Issue と承認済みの補足事項に照らし合わせます。変更がリポジトリの命令に従っていることも確認します。
3. lint、単体テスト、E2E テスト、型チェックの出力を調べます。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解消し、影響を受けたチェックを再実行します。Playwright の E2E 設定はプレビューをビルドして配信し、ローカル サーバーを再利用できます。以前のレッスンのサーバーではなく、この worktree のサーバーがテスト対象であることを確認します。

## 新しい機能を試す

コードに問題がないように見えても、実際に動くか確認します。前と同じようにアプリを起動し、ブラウザー Canvas でサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザー Canvas で開くよう Copilot に依頼します。

   ```plaintext
   Start the app and open it in the browser canvas.
   ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザー ウィンドウが開きます。
3. カテゴリを選択し、該当する結果だけが表示されることを確認します。フィルターをクリアしてから発行元を選び、結果がその発行元に合っていることを確認します。
4. カテゴリと発行元を組み合わせ、結果を Issue と承認済みの計画に照らし合わせます。複数カテゴリがサポートされる場合は、合意した組み合わせの動作も確認します。
5. 一致するゲームがない組み合わせを試し、空の状態を確認します。フィルターをクリアまたはリセットして、全件が再表示されることを確認します。
6. 終わったら、次のプロンプトでこのセッションが起動した開発サーバーを停止するよう Copilot に依頼します。

   ```plaintext
   Stop the dev server and close the browser canvas.
   ```

## 次のレッスンのためにセッションを残す

フィルタリングの PR は、まだ作成またはマージしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次はカスタム命令をフィルタリングのコードに適用し、スキルと QA の改善を追加してから、レッスン 8 で変更をまとめた PR を作成してマージします。サーバーを停止した後はセッションをそのまま残し、次のレッスンで再開してください。
